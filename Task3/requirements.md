# Требования к интеграции «Умного дома»

На диаграмме контейнеров две вкладки: полный ландшафт и подробная схема интеграции. Существующее приложение собственников сохраняется. Новые компоненты относятся к домену ЖКУ; продажи, финансы и аналитика не получают доступ к биометрии.

## Взаимодействие

1. **Ручное открытие:** приложение → tenant-core-app → smart-home-adapter → партнёр → устройство. Сервер проверяет собственника, УК, дом, устройство и разрешение. Принятие команды не подтверждает открытие: результат приходит отдельным событием с commandId.
2. **Автоматическое открытие:** устройство → распознавание у партнёра → проверка актуального разрешения для дома → открытие → событие в callback-api → аудит. Отозванные и просроченные разрешения не используются; при потере связи автоматическое открытие запрещается. Механический и аварийный выход не блокируется.
3. **Регистрация биометрии:** после отдельного согласия приложение получает одноразовую ссылку регистрации у партнёра. Фото/шаблон передаются непосредственно в допустимый контур обработки партнёра, минуя tenant-core-app. PropDevelopment хранит enrollmentId и сведения о согласии. Биометрические шаблоны при этом не становятся анонимными.
4. **Разрешения:** tenant-core-app сверяет связь собственника с объектом в CRM. Адаптер передаёт разрешение с buildingId, deviceId, subjectRef и сроком действия. Смена собственника, отзыв согласия или доступа вызывает отзыв у партнёра и устройства; до подтверждённого отзыва устаревшее разрешение использовать нельзя.

5. **Вызов домофона:** событие вызова поступает через callback-api в существующее приложение. После проверки прав приложение получает короткоживущий токен только этого вызова; видео передаётся напрямую с платформы партнёра по WebRTC (DTLS-SRTP). Сигналинг — HTTPS/WSS. Для открытия используется отдельная проверенная команда; ссылка на поток не даёт прав на дверь.

## Обязательные требования

| Область | Требование и способ проверки |
|---|---|
| Собственник | OIDC Authorization Code + PKCE через auth-service-1, короткая сессия и безопасное хранение токенов в приложении. Проверка issuer, audience, подписи и срока access token. |
| Межсервисный доступ | OAuth 2.0 Client Credentials и mTLS между адаптером и партнёром. Отдельный клиент для каждой УК/партнёра, без общих секретов. Это не заменяет проверку прав собственника. |
| Авторизация API | Scopes door:open, barrier:open, access:manage, events:write. Проверять subjectRef → УК → дом → устройство для каждой команды и события. companyId из тела запроса не является доверенным. |
| Изоляция УК | УК определяется по проверенному токену и реестру интеграций. Чтение, изменение и открытие чужого объекта должны завершаться отказом — проверить отрицательными тестами. |
| Периметр | API Gateway/WAF перед callback-api; исходящий доступ адаптера только к разрешённым адресам партнёра. Нет прямого доступа партнёра к CRM, БД, DWH или Kubernetes API. |
| Каналы | TLS 1.2/1.3 с проверкой цепочки и имени сертификата. Взаимная аутентификация устройств и платформы. Незашифрованные каналы не допускаются. |
| Контракты | Allowlist полей, валидация схемы и размера. Передавать только идентификаторы, разрешение и необходимые данные регистрации; исключить паспорт, финансовую историю и полную карточку CRM. |
| Callbacks | mTLS и сервисный JWT, проверка tenant/object scope, eventId, timestamp и окна доставки. Дедупликация повторов и отказ для устаревших событий. |
| Команды | Короткий TTL, commandId/idempotency key, тайм-ауты и ограниченные повторы с тем же ключом. Поздняя доставка не открывает дверь после истечения разрешения. Неопределённый результат не считается успехом. |
| Нагрузка | Лимиты на пользователя, партнёра и устройство; защита от перебора идентификаторов и массовых команд, мониторинг аномалий. |
| Секреты | Защищённое хранилище, минимальные права, ротация и аудит. Ключи не попадают в Git, логи или конфигурацию мобильного клиента. |
| Биометрия | Секретный класс: фото и шаблоны не попадают в CRM, логи, резервные копии PropDevelopment или DWH. У партнёра — изолированное шифрованное хранение и управляемое удаление. |
| Госномера | Номер автомобиля, связанный с собственником, — персональные данные. Использование только для въезда; в логах vehicleRef вместо открытого номера. |
| Согласие | Фиксировать цель, состав данных, получателей, версию согласия и срок обработки. Обеспечить исправление, отзыв и подтверждённое удаление у партнёра/субподрядчиков, включая порядок очистки копий. |
| Правовые основания | До включения распознавания лиц согласовать допустимую схему и статус поставщика по 152-ФЗ (в том числе ст. 11) и 572-ФЗ. Договора API или шифрования недостаточно. Проверить требования к размещению, согласиям и биометрической системе. |
| Альтернатива | Отказ от распознавания лица не лишает обычного доступа: остаются звонок, ключ/карта и приложение. При недопустимой схеме обработки биометрическая функция не включается. |
| Аудит | Фиксировать subjectRef, УК, дом, deviceId, операцию, результат, commandId/eventId и время. Защита от подмены; без биометрии, токенов и полного payload. |
| Допуск партнёра | Зафиксировать роли оператора/обработчика, субподрядчиков, цели/сроки обработки, защиту и уведомление об инцидентах. Проверить восстановление, обновления устройств и отзыв доступа. |

Сроки хранения и показатели восстановления утверждаются владельцем данных и ИБ до запуска. В аналитику передаются только необходимые агрегаты без возможности выделить собственника.

Основания: [152-ФЗ, статья 11](https://base.garant.ru/12148567/9d78f2e21a0e8d6e5a75ac4e4a939832/), [572-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_436110/).
