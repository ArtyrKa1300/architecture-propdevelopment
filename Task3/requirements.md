# Требования к интеграции «Умного дома»

Используется текущее приложение собственников. Новые компоненты относятся к домену ЖКУ. На диаграмме контейнеров две вкладки: общий ландшафт и связи интеграции.

## Взаимодействие

1. **Открытие из приложения:** приложение → tenant-core-app → smart-home-adapter → платформа партнёра → домофон или шлагбаум. Перед отправкой проверяются права собственника на дом и устройство. Результат команды возвращается событием с commandId.
2. **Автоматическое открытие:** партнёр распознаёт лицо или номер автомобиля, проверяет действующее разрешение и открывает устройство. Событие передаётся в callback-api. При отсутствии актуального разрешения автоматическое открытие запрещено; аварийный выход остаётся доступен.
3. **Регистрация и отзыв доступа:** приложение получает одноразовую ссылку регистрации у партнёра после согласия собственника. Фото и биошаблоны обрабатываются у партнёра; PropDevelopment хранит enrollmentId, согласие и разрешения. Смена собственника или отзыв согласия отменяет доступ у партнёра и устройства.
4. **Видеозвонок:** callback-api передаёт событие вызова в приложение. После проверки прав выдаётся короткоживущий токен конкретного вызова. Видео идёт напрямую от партнёра по WebRTC; открытие двери требует отдельной команды.

## Безопасность

| Область | Требование |
|---|---|
| Пользователь | OIDC Authorization Code + PKCE через auth-service-1. Проверять подпись, issuer, audience и срок токена. |
| Межсервисный доступ | OAuth 2.0 Client Credentials и mTLS. Отдельные учётные данные для каждого партнёра/УК. |
| Авторизация | Для каждой операции проверять пользователя, УК, дом и устройство. Scopes: door:open, barrier:open, access:manage, events:write. Отказ при попытке доступа к чужому объекту. |
| Каналы и периметр | HTTPS/TLS с проверкой сертификатов; WebRTC с DTLS-SRTP, сигналинг HTTPS/WSS. Входящие события через API Gateway/WAF. Партнёр не получает прямой доступ к CRM, БД и Kubernetes. |
| Данные | Передавать только необходимые идентификаторы и разрешения, проверять схему и размер запроса. Не передавать полную карточку CRM, паспортные и финансовые данные. |
| Команды и события | commandId/eventId, ограниченный срок действия, дедупликация и безопасные повторы. Проверять подлинность и время события; просроченная команда не открывает дверь. |
| Секреты | Хранить в защищённом хранилище, ограничить доступ и настроить ротацию. Не включать ключи и токены в Git, приложение или логи. |
| Биометрия и номера | Фото и биошаблоны не попадают в CRM, DWH и логи PropDevelopment. У партнёра — шифрование, ограничение доступа и удаление. Госномера используются только для въезда; в логах — vehicleRef. |
| Согласие | Фиксировать цель, состав данных и срок обработки. Обеспечить отзыв доступа и подтверждение удаления у партнёра. До запуска согласовать с ИБ и юристами схему обработки по 152-ФЗ и 572-ФЗ. Доступ по ключу, звонку или приложению сохраняется без биометрии. |
| Аудит | Записывать пользователя, УК, дом, устройство, операцию, результат, время и commandId/eventId. Защищать журнал от изменения; не записывать биометрию, токены и полные запросы. |
| Защита API | Ограничивать частоту запросов на пользователя, партнёра и устройство. Контролировать попытки доступа к чужим объектам и массового открытия. |
| Партнёр | Согласовать ответственность, субподрядчиков, размещение и сроки хранения данных, отзыв доступа и порядок уведомления об инцидентах. |
